# WIIE Excellence Standard v1.0

**WPA Institutional Intelligence Engine**  
**Internal effectiveness, efficiency, observability and continuous-improvement standard**  
**Date:** 5 October 2026  
**Status:** Internal governance and evaluation framework

## 1. Objective

WIIE should become progressively more useful, faster, more selective, more traceable and more resilient without becoming more autonomous in the constitutional sense.

The optimization target is not “maximum automation”. It is:

> **Maximum verified institutional value with the minimum justified activation, duplication, latency and rework — under unchanged human authority.**

## 2. Two separate questions

### Effectiveness
Did WPA solve the right problem with adequate evidence, correct authority boundaries and a useful institutional result?

### Efficiency
Did WPA reach that verified result with only the specialist profiles, sources, tools, time and rework that were actually justified?

A fast wrong answer is ineffective.  
A correct answer produced through unnecessary institutional machinery is inefficient.  
WIIE must optimize both.

## 3. Five mission profiles

### L0 — Lightweight
Low-consequence clarification, routing or simple protocol check. Minimal specialist activation. No Futures cycle unless a real trigger exists.

### L1 — Standard
Bounded research, briefing or analysis. Targeted verification and limited specialist routing.

### L2 — Institutional
Strategy, architecture, programme, policy or major cross-domain work. System map, three materially different options, Futures stress test and adversarial review are required.

### L3 — Consequential
Production-changing, public, legal, financial, privacy-sensitive or external-commitment work. Human Gate, staged implementation, regression testing and rollback planning are mandatory where technically applicable.

### L4 — Constitutional / Doctrine
Doctrine, new authority, foundational rule or constitutional identity. WIIE is advisory only until explicit HG4 human authorisation.

## 4. Minimal sufficient activation

Every specialist activation must have a routing reason.

WIIE should:
- reuse a verified WPA asset before repeating external research;
- avoid duplicate source discovery;
- parallelise only independent work;
- activate Architect/Mentor/Reviewer depth only when mission profile warrants it;
- avoid Council-80/full-council execution unless a documented reason exists;
- treat over-routing as an efficiency defect.

## 5. Early exit

A WIIE mission may exit before all stages only when:
- the objective is already resolved;
- evidence is sufficient for the consequence class;
- no material contradiction remains;
- no consequential side effect is requested;
- no Human Gate escalation exists;
- future uncertainty would not materially alter the result.

Early exit is forbidden when source rights, provenance, mandate or high-consequence uncertainty remains unresolved.

## 6. Observability

L2–L4 missions should produce a governed run record containing, where applicable:
- problem and mission profile;
- consequence/Human Gate class;
- routing reasons and active specialists;
- source/provenance state;
- options and scenario stress test;
- AI PROTOCOL Gate state;
- implementation and rollback reference;
- adversarial findings;
- verification state;
- timing/tool-use/cost data when technically available;
- measured outcome;
- correction and learning candidates.

Observability must remain privacy-minimising. “More logging” is not automatically better.

## 7. Effectiveness metrics

Candidate measures:
- objective completion;
- verified evidence coverage;
- provenance completeness;
- Human Gate compliance;
- first-pass verification;
- implementation success;
- measured outcome improvement;
- repeat-error reduction;
- contradiction escape reduction;
- human reviewer acceptance/revision signal.

## 8. Efficiency metrics

Candidate measures:
- time to verified result;
- number of specialist profiles activated;
- unnecessary specialist activation;
- tool calls per verified result;
- duplicate research;
- verified asset reuse;
- rework ratio;
- correction-loop time;
- first-pass success;
- cost per successful mission when reliable cost data exists.

No numeric performance claim is permitted before WPA has a measured baseline.

## 9. Change safety

Material production changes should use:
1. pre-change version reference or snapshot;
2. staged/canary introduction where practical;
3. regression tests;
4. explicit rollback plan;
5. post-change verification;
6. outcome measurement.

A speed improvement that causes a material regression in evidence quality, mandate integrity, Human Gate correctness or outcome quality is a failed optimization.

## 10. Evaluation flywheel

Before a material WIIE routing/runtime change:
1. run the canonical benchmark suite;
2. compare against the previous canonical version;
3. inspect failures and route-selection changes;
4. reject changes that weaken source discipline or authority integrity;
5. promote only evidence-backed improvements;
6. capture verified lessons for human-reviewed reintegration.

This is intentionally aligned with the general engineering logic of traces, repeatable evaluation datasets, guardrails and human review used in contemporary agent systems, while remaining a WPA-owned method.

## 11. External-framework boundary

WPA may learn from:
- agent tracing/evaluation and human-review practices;
- NIST AI risk-management and TEVV concepts;
- ISO/IEC 42001 management-system concepts such as continual improvement, transparency and risk/opportunity management.

These are methodological reference points only. WPA does **not** claim ISO certification, NIST endorsement, OpenAI endorsement or formal conformity merely by referencing them.

## 12. Constitutional invariant

> **Self-improving does not mean self-governing.**

WIIE may improve routes, tests, reusable assets and working procedures through verified learning. It may not silently change doctrine, expand its own mandate or convert machine consensus into institutional will.

> **Code may become liquid; the mandate must not.**
